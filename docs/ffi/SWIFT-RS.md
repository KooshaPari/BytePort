# BytePort — swift-rs 0.1 v8.2 Walkthrough

## The mismatch

The original scaffold release of the macOS share-ext FFI
(`ffi/macos-share/build.rs`) shipped with the following comment:

```rust
//   swift_rs::SwiftLinker::new("10.15")
//       .with_package("byteport-share", "src/main.swift")
//       .link();
```

That code shape is from a *newer* swift-rs line. The actual API
surface of the `swift-rs = "0.1"` line we pin in `Cargo.toml` is
fundamentally different:

```rust
use swift_rs::build_utils::{link_swift, link_swift_package};

link_swift();                              // wires Swift runtime libs
link_swift_package("byteport-share", "src"); // `swift build` rooted at src/
```

Two consequences:

1. **No single-file compilation.** swift-rs 0.1 expects a proper Swift
   Package Manager layout: `Package.swift` + `Sources/<target>/...`.
   The old `src/main.swift` (single-file compilation) is gone.
2. **The 0.1 API runs `swift build`.** That invokes the Swift toolchain
   for real, which is heavy. We want `cargo check --workspace` to stay
   cheap and Swift-free on PR runs.

## v8.2 layout

```
ffi/macos-share/
├── build.rs                                  ← uses swift_rs::build_utils
├── Cargo.toml                                ← swift-rs 0.1 (macOS-gated) + link-swift feature
└── src/
    ├── lib.rs                                ← Rust FFI bridge (extern "C")
    ├── Package.swift                         ← swift-rs 0.1 entry point
    └── Sources/
        └── byteport-share/
            └── main.swift                    ← moved here from src/main.swift
```

## Usage

| Command | Effect |
| --- | --- |
| `cargo check --workspace` | Default. Skips the Swift step. Fast (sub-second on macOS). |
| `cargo build -p byteport-macos-share --features link-swift` | macOS-only. Invokes `swift build -c release` inside `src/`. |
| `cargo build --target x86_64-pc-windows-msvc` | Linux/Windows. No swift-rs resolve, no Swift compile. |

## Why the `link-swift` feature gate

A PR that touches `ffi/macos-share/build.rs` should not force every CI
runner to compile Swift sources via `swift build`. The default
`cargo check --workspace` path stays Swift-free, while an explicit
`--features link-swift` opt-in (used by the cross-compile CI matrix)
runs the real Swift pipeline.

## API mismatch reference table

| Surface | swift-rs ≥ 0.2 (newer) | swift-rs 0.1 (pinned) |
| --- | --- | --- |
| Entrypoint | `swift_rs::SwiftLinker::new("10.15")` | `swift_rs::build_utils::link_swift_package(name, root)` |
| Source layout | `.with_package(name, "src/main.swift")` | `Package.swift` + `Sources/<name>/` |
| Output | static lib + C header in `$OUT_DIR` | `PackageName/.build/<triple>/<profile>/libPackageName.a` |
| API style | OOP builder | free function |

## Future work

- Bump to `swift-rs = "1"` (now stable) and rewrite build.rs against the
  newer `SwiftLinker` API. Tracked in DEBT-WIN-005.
- Surface the C header generated by swiftc in `OUT_DIR` to the Rust
  `lib.rs` `extern "C"` block, replacing the manual `byteport_share.h`
  artifact.

## Known issue: swift-rs 0.1 RPath panic

On a Mac with a recent Xcode toolchain (≥ 13, Swift 5.7+),
`link_swift()` (called inside `link_swift_package`) panics with:

```
thread 'main' panicked at build_utils.rs:48:9:
Libraries require RPath! Change minimum MacOS value to fix.
```

The root cause is hardcoded inside swift-rs 0.1:

```rust
// swift-rs 0.1/src-rs/build_utils.rs
const MACOS_TARGET_VERSION: &str = "11";
```

swift-rs 0.1 calls `swift -target <arch>-apple-macosx11
-print-target-info` and panics if the host toolchain reports
`libraries_require_rpath: true` (the modern default). The only paths
to lift this limitation:

1. **Use Xcode ≤ 13.4 / Swift ≤ 5.7** — older toolchains report
   `libraries_require_rpath: false`. Not viable for an active dev host.
2. **Bump to swift-rs ≥ 1.0** — the line this scaffold skips because of
   the v8.2 API mismatch.
3. **Run on an Apple Silicon Mac running macOS ≤ 11 Big Sur** — no
   modern dev host qualifies.
4. **Pin to a custom swift-rs fork** with `MACOS_TARGET_VERSION = "12"`
   or higher — invasive.

For the v8.2 scaffold release, the **default `cargo check --workspace`
path is Swift-free and passes everywhere**. The `link-swift` feature is
wired correctly; the upstream RPath panic is a known limitation that
follows in DEBT-WIN-005 once we migrate to swift-rs 1.x.
